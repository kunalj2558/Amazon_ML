# Feature Engineering and Model Training Plan

## 1. Objective

Convert each candidate pair into a high-quality feature vector and train a pairwise classifier optimized for the actual competition objective.

The core model should initially be a gradient-boosted tree classifier because the data combines heterogeneous numeric, categorical, string-similarity, structural and retrieval signals.

Neural reranking is an optional second stage, not a prerequisite for a valid solution.

## 2. Training unit

One training row represents:

```text
(S1 record, S2/S3 candidate record)
```

Label:

```text
1 = ground-truth match
0 = candidate but not a ground-truth match
```

The negative class should primarily come from the actual blocking candidate set.

## 3. Split strategy

Split by Source 1 entity, not by pair.

Recommended:

```text
70% S1 entities -> train
15% S1 entities -> validation
15% S1 entities -> final local test
```

Ensure country and match-cardinality distributions are reasonably represented.

Never allow pairs from the same S1 entity to appear across train and validation.

Store features generated by blocking:

```text

bm25_rank
semantic_score
semantic_rank

```

These are valuable because a candidate retrieved independently by multiple mechanisms has more evidence than one retrieved by a single weak blocker.

### F. Interaction features

Examples:

```text

```

Do not hard-code arbitrary thresholds without validation.

## 5. Feature engineering rules

For every feature:

- define behavior for missing values;
- avoid NaN leakage;
- keep the raw comparison interpretable;
- avoid features that depend on ground-truth labels;
- document the formula.

Do not create a feature using test labels or external data.

## 6. Model 1 — LightGBM

Initial search space:

```text
learning_rate: 0.02–0.08
num_leaves: 31–255
min_child_samples: 20–150
feature_fraction: 0.6–1.0
bagging_fraction: 0.6–1.0
n_estimators: 300–2000
```

Use early stopping.

Primary model-selection metric:

```text
validation macro F0.5 after threshold optimization
```

Do not select the model solely on AUC.

AUC may be logged, but the competition objective is F0.5.

## 7. Class imbalance

Do not blindly use all possible negatives.

Use:

```text
all positives
+
hard negatives
+
a controlled sample of easy negatives
```

Start around:

```text
1 positive : 5 hard negatives
```

Then test alternatives such as 1:10 or 1:20 if validation indicates benefit.

Use class weights only after checking their effect on calibration.

## 8. Model 2 — semantic score

If multilingual embedding retrieval is implemented, retain its cosine similarity as a feature.

Use:

```text
name embedding cosine
address embedding cosine
combined embedding cosine
```

Do not assume a cosine threshold such as 0.92 is universally correct. Tune it on validation data.

## 9. Model 3 — cross-encoder reranker

Use only if time/compute allows and validation shows a gap after LightGBM.

Input:

```text
[record A name] [record A address] [record A country]
[SEP]
[record B name] [record B address] [record B country]
```

Train using positive matches and hard negatives.

Apply it only to top-ranked candidates after the cheaper model.

This avoids running an expensive neural model over every candidate.

## 10. Ensemble

Start simple:

```text
final_score =
    w1 * calibrated_lgbm
  + w2 * normalized_semantic
  + w3 * cross_encoder
```

Tune weights on the validation entity set.

Do not assume weights such as 0.4/0.2/0.4 are optimal.

If the cross-encoder adds no validation improvement, remove it.

## 11. Calibration

Because the final decision is threshold-based, score calibration matters.

Compare:

- raw LightGBM probability;
- Platt/logistic calibration;
- isotonic calibration if enough validation data exists.

Select based on entity-level F0.5, not visual probability quality.

## 12. Feature ablation

Run controlled experiments:

```text
baseline string features
+ address features
+ phonetic
+ retrieval
+ semantic
+ interactions
```

Record:

```text
feature_set
validation_F0.5
precision
recall
runtime
```

Remove features that increase complexity without useful validation improvement.

## 13. Error analysis

Create four buckets:

1. False positive on singleton.
2. False positive on multi-match entity.
3. False negative inside candidate set.
4. True match missing from candidate set.

The fourth category is not a model problem. It is a blocking problem.

The first category is a threshold/calibration problem.

This separation prevents wasting time tuning the wrong component.

## 15. Acceptance criteria

The model stage is complete when:

```text
[ ] Positives are complete
[ ] Negatives are blocker-derived
[ ] Entity-level split is used
[ ] No validation leakage
[ ] Feature calculations are deterministic
[ ] F0.5 is computed exactly at entity level
[ ] Best threshold is stored
[ ] Model can score the complete candidate set
```

## 16. Practical priority

Given a three-day challenge:

1. LightGBM + strong string/address features.
2. Hard negatives.
3. Better blocking.
4. Threshold optimization.
5. Semantic embeddings.
6. Cross-encoder only if the first five are already stable.

A complex model that cannot be validated and submitted safely is less useful than a simpler model with reliable F0.5.
